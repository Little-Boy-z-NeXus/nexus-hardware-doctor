# H05/H06: bounded diagnosis and nonphysical action verification

The backend can run an observe → plan → policy → execute → verify loop. Every run is bounded by an action count, deadline and retry budget. It produces canonical v1 lifecycle events linked to the session trace and tool-call IDs. A failed tool can provide evidence of a tool error, but cannot establish a successful measurement or repair.

`run_diagnosis(context, planner, mode="mock", max_steps=6, timeout_seconds=30, trace_id=None)` returns status, structured plan, evidence observations, audit events, action count, source and verification scope. The optional adapter, policy and initial-observation parameters support offline tests and evaluation; the HTTP interface does not expose those injection points. Initial observation fixtures require an explicit simulator source and matching device ID.

## Available operations

| Operation | Real mode | Mock mode |
| --- | --- | --- |
| `get_hardware_graph` | Read validated context topology | Same context read |
| `get_telemetry` | Fresh N03 read when explicitly bound; otherwise saved context snapshot | Read sandbox snapshot |
| `set_pwm` | Manual required; no physical command | Bounded in-memory PWM change |
| `enable_driver` | Manual required; no physical command | Bounded in-memory driver change |
| `run_motor_test` | Manual required; no physical command | Synthetic active sample followed by stopped sample |
| `read_gpio` | Blocked; adapter unavailable | Blocked; adapter unavailable |
| Unknown tools or extra arguments | Blocked | Blocked |

The sandbox copies its input. It has no database connection or device transport. A simulated change never updates registered device telemetry or another diagnosis. Mock mode accepts only simulator telemetry, and supplemental evaluation observations are labeled as supplied simulation fixtures. Real mode may read device or replay context; an explicitly bound serial adapter can perform N03 reads, but cannot issue motor writes, even through an injected permissive policy.

## Deterministic safety policy

The policy classifies requests as `read_only`, `auto_safe`, `manual_required` or `blocked`. Each tool has exact required and permitted arguments. Boolean values do not count as numeric arguments. Read capabilities in a hardware document do not enable a device adapter.

Simulated actions require a matching before sample with a timestamp no older than five seconds and no more than one second into the future. A null timestamp, replay source, missing sample or mismatched device/model blocks a write. PWM must remain between zero and the declared maximum. Test durations must remain between 100 ms and the declared maximum. The absolute current must remain within the declared limit. Bus voltage must remain above the declared minimum and at or below the explicit simulator ceiling of 14 V.

The 14 V ceiling is a nonphysical sandbox setting, **not a component voltage rating**. Frozen v1 lacks per-pin electrical ratings and maximum bus voltage. Physical action approval still requires those missing resources, supervised command integration and actual before/after verification. The new N03 read path does not enable those actions.

## Verification and failure behavior

An acknowledgement cannot pass verification. The verifier requires distinct, fresh, device-bound simulator samples in increasing sequence and time order. `set_pwm` and `enable_driver` must show the requested field changing to the requested value. A repeated no-op fails verification. A motor test must show an active synthetic sample and then a stopped sample with zero PWM and disabled driver. Its duration is simulated; the adapter does not wait or drive a motor. Synthetic current is calculated solely for testing, and `motor_rpm` remains null.

Verification produces `verification.passed` or `verification.failed` events with `scope: "simulation"` and `physical_operation_verified: false`. A provider's `diagnosed` stop requires evidence IDs bound to known samples or successful observations. Failed-observation IDs can support only a `tool_error` hypothesis and cannot support a diagnosed result. A diagnosis supported by reads is distinct from a verified simulated change; the result reports the number of verified changes explicitly.

Read tools and planner failures can retry within the configured budget; simulated writes never retry automatically. Unverified write outcomes stop for manual review. Repeated identical tool requests, exhausted action budgets, invalid evidence, unknown tools and expired deadlines stop the run. Result summaries never claim physical operation has been verified.

```bash
python -m pytest backend/tests/test_policy.py backend/tests/test_orchestrator.py -q
```

Tests cover default denial, exact arguments, electrical and timing bounds, source/device isolation, before/after verification, failed acknowledgements, missing and stale samples, tool recovery, timeouts, loops, motor-test stop behavior and trace/event linkage. Passing these checks establishes software behavior. Full H05/H06 hardware acceptance still requires supervised write integration and observed physical verification.

## N03 read and history integration

Hoàng is the integrator for this H05/H06 backend change. It consumes Nguyễn's existing
N03 protocol without changing firmware or the frozen Tool Call v1 contract.

Set `NEXUS_SERIAL_DEVICE_ID` to an existing registered device whose source is `device`
and whose hardware model matches the connected firmware. Leave it blank to retain the
standalone live monitor. Registration is explicit: serial traffic cannot create a device,
change its configuration/source, or replace old history. Status is available through
`/api/diagnosis/capabilities` as `serial_history_status`.

The existing serial bridge owns the only port handle. Its worker receives telemetry and
dispatches one bounded read at a time. Canonical `get_telemetry` maps to N03 `read_current`,
which supplies measured current and full before/after snapshots. The canonical
`tool_call_id` is copied unchanged into `request_id`. A matching accepted ACK, valid
effect-free result, and a subsequent canonical telemetry frame are all required. The
result and frame must arrive on the same connection/device/model. Cached duplicate
results, mismatched IDs, missing results, bad values, disconnects and resets cannot pass.

The complete read has a three-second deadline, bounded by the diagnosis deadline.
Cancellation removes unsent work; reconnect never replays an old request. Read retries
retain the same tool ID, and a cached response cannot be counted as a fresh measurement.
Busy, timeout and device failures produce failed observations through the existing
recovery loop. GPIO and motor actions remain unavailable through this adapter.

Incoming telemetry is saved atomically with an audit event. Host receipt time,
connection ID and the original firmware sample ID are recorded as provenance. Persistent
sample IDs are namespaced per connection/reset because firmware reuses IDs after reboot.
The firmware sequence and `recorded_at` are preserved; null device time stays null.
Command snapshots have no canonical identity/time and are never invented into samples.
Successful reads are saved before the planner receives them, and the next planning step
includes the fresh frame. Session observations preserve the command/measurement link.

Software tests use an in-memory N03 port with deliberately split serial frames. They
exercise the actual bridge thread, API, policy, SQLite history and WebSocket, without
opening USB, calling Nebius or moving a motor:

```bash
python -m pytest backend/tests/test_serial_reads.py backend/tests/test_serial_integration.py -q
```

The firmware's identity string is a configured association, not cryptographic hardware
attestation. Physical wiring, calibrated limits and operation on the actual rig remain
unverified. `physical_commands_enabled: false` continues to mean motor writes are disabled.
